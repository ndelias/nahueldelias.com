<BodySection label="The problem" heading="The code doubled. Review didn't speed up.">
  In a year, merge requests at GitLab that disclose AI help went from 3% to 22%, and the code in each change doubled, from 37 lines to 76. Review isn't slow. It just didn't get any faster, so reviewers kept pace by reading less: review comments per line fell 38%. Review has to speed up to match the code, without people approving what they haven't read.
</BodySection>

<Figure src={whyNow} alt="Two charts: merge requests disclosing AI help rising to 22% by month, and lines changed per merge request climbing to 76 while time to merge stays flat." caption="Measured on GitLab's product repo, which is developed in public" />

<BodySection label="Research first" heading="I let the data pick the product.">
  I started with a different idea, Blast Radius. Before building anything, I wrote down how I'd test it, then pulled 78,276 public posts and 105,397 merge requests, and coded 2,000 posts at random. Blast Radius came last. Reviewers drowning in AI-written code came first.

  Every plan was committed before its data, and every number on the site links back to it, including the hypotheses that turned out wrong.
</BodySection>

<Figure src={ranking} alt="Twelve pains ranked by score. AI-written code needing cleanup and overloaded code review tie at the top; non-engineers depending on engineering, my original idea, is last." caption="Twelve pains, scored on the same rules. My first idea is the grey bar at the bottom" />

<BodySection label="The product" heading="Faster reviews, without skipping the reading.">
  Vera sits above the review bots and organizes each pull request so it moves faster. It maps what the change touches and shows reviewers what to look at first, including likely AI-written code nobody has checked. Each role gets a brief instead of the whole diff, and can ask Vera about the code; it answers with the lines it used. Design, security and product are asked to sign off at the same time, not one after another.

  The speed comes with a check: on risky changes, the reviewer answers a couple of questions, and the result is recorded on the approval. Rules in the repo, not a model, decide who has to approve.
</BodySection>
